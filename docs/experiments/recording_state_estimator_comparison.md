# Recording PX4, MoCap estimator, and raw MoCap

The recorder now retains the three state sources required to diagnose real
experiments:

```text
/<robot>/fmu/out/vehicle_odometry   # PX4 estimate
/mocap/<robot>/pose                 # raw incoming MoCap pose
/mocap/<robot>/pose_core            # raw MoCap after frame calibration
/mocap/<robot>/odom_ekf             # MoCap estimator output
```

It also retains the configured gyro topic plus the common hardware/SITL gyro
topics when present.

## Why `pose_core` is the comparison reference

The incoming real MoCap pose may use a different world origin, world basis, or
rigid-body basis. Plotting it directly against PX4 would therefore mix frame
errors with estimator errors.

`/mocap/<robot>/pose_core` is generated by the estimator's input transform and
is always

```text
world = core NWU
body = FLU
```

so all three plotted sources are expressed in the same convention.

## Recorder arguments

Relevant state arguments:

```text
--state-source px4|nav_msgs
--state-topic-template TEMPLATE
--mocap-world-frame core_nwu|ros_enu
--odom-twist-frame body|world
--ekf-topic-template TEMPLATE
--mocap-pose-topic-template TEMPLATE
--mocap-core-pose-topic-template TEMPLATE
--imu-topic-template TEMPLATE
```

For the revised MoCap estimator, controller-facing Odometry is always
core-NWU/body-FLU, so use

```text
--mocap-world-frame core_nwu
--odom-twist-frame body
```

## Hardware EKF-controlled recording

```bash
scripts/record_formation_experiment.sh \
  --name two_robot_experiment_ekf \
  --robots splash,glub \
  --edge glub:splash \
  --state-source nav_msgs \
  --state-topic-template '/mocap/{robot}/odom_ekf' \
  --mocap-world-frame core_nwu \
  --odom-twist-frame body \
  --imu-topic-template '/{robot}/mavros/imu/data'
```

## Exported arrays

The normal controller-state arrays remain:

```text
positions
quaternions
linear_velocity_body
angular_velocity_body
```

Parallel PX4 arrays:

```text
px4_positions
px4_quaternions
px4_linear_velocity_body
px4_angular_velocity_body
```

Parallel MoCap-estimator arrays:

```text
ekf_positions
ekf_quaternions
ekf_linear_velocity_body
ekf_angular_velocity_body
```

Transformed raw MoCap:

```text
mocap_positions
mocap_quaternions
mocap_linear_velocity_body_fd
mocap_angular_velocity_body_fd
```

The two `*_fd` arrays are finite-difference diagnostics reconstructed from raw
MoCap pose. They are not measured twists and are never fed back to the
controller.

## Comparison plots

`plot_experiment.py` automatically invokes

```text
plot_state_estimator_comparison.py
```

for initialization and mission histories.

For every robot it generates:

```text
estimator_state_comparison_<robot>.<format>
estimator_disagreement_<robot>.<format>
```

The state figure contains:

1. position: PX4 / estimator / raw MoCap;
2. body linear velocity: PX4 / estimator / raw MoCap FD;
3. pairwise attitude disagreement;
4. body angular velocity: PX4 / estimator / raw MoCap FD.

The disagreement figure contains all available pairwise errors:

```text
PX4 - estimator
PX4 - raw MoCap
estimator - raw MoCap
```

for position, attitude, linear velocity, and angular velocity.

This is intended to make real-experiment failures classifiable:

- PX4 differs from both MoCap streams -> likely PX4 state issue;
- estimator differs from PX4 and raw MoCap -> estimator/tuning issue;
- raw MoCap itself jumps/noises -> measurement or frame-calibration issue;
- all three agree but control is poor -> controller/model/actuation issue.

Older bags without `/pose_core` remain supported; the plotter falls back to the
two-observer PX4-vs-estimator comparison.
